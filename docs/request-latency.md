# O!RIVANE: время ответа и сравнение моделей, 28.10.2026

Последующее исправление протокола и транспорта с 34/35 полными LLM-успехами: [исправление ядра](core-reliability.md). Ниже сохранены исторические измерения до исправления.

## Реализовано

- Один монотонный deadline: обычный запрос 10 с (цель 3–5 с), пересборка существующей поездки с несколькими изменениями 15 с, альтернативы 20 с. HTTP-граница включает загрузку/нормализацию, разбор, поиск, инструменты, сохранение и кодирование ответа. На сохранение резервируется до 250 мс.
- Поиск возвращает проверенные факты сразу. Персональное объяснение запускается отдельно в оставшемся времени исходного запроса. Отдельный endpoint возвращает только `agent`, проверяя revision до и после ожидания. Он не меняет условия, выбор, историю и заказ.
- Устаревшие задачи отменяются, одинаковые запросы используют одну задачу. Готовые объяснения другой поездки не вытесняются случайным сохранением. После ошибки изменения интерфейс возобновляет загрузку объяснения. Обновляется только панель: текст, фокус и карточки сохраняются.
- Отмена не ждёт медленного закрытия соединения. Рабочие копии изолированы: поздний поиск не публикует изменения. При таймауте доступны локально проверенные результаты с честным уведомлением; режим не называется LLM.
- SQLite при конфликте блокировки завершает ограниченный запрос сразу. Проверены блокировки UPDATE и COMMIT, отсутствие позднего сохранения и очистка соединения после неудачного COMMIT. PostgreSQL получает statement_timeout; исполнение с настоящим PostgreSQL не проверено.

Конфигурация модели остаётся `LLM_MODEL`; адрес MultiAI и ключ не менялись. Локальная основная модель — `gpt-5.6-luna`; Compose и `.env.example` приведены к тому же значению.

## Парное сравнение: по 40 сценариев

Артефакт: `artifacts/haiku-luna-latency-40.json`. Сценарии выполнялись последовательно, порядок моделей чередовался. Использовались производственные запросы, JSON-парсер, доменная валидация, Decision-протокол и проверка фактов. На каждую модель — 40 пользовательских сценариев, из них 35 требуют модели и 5 намеренно локальны. Реальных HTTP-вызовов: Haiku 52, Luna 46 (несколько стадий и ограниченные исправления схемы).

| Метрика | Claude Haiku 5.5 | GPT-5.6 Luna |
|---|---:|---:|
| Первый результат обычного запроса, p50 / p95, с | 4,016 / 10,016 | 3,391 / 10,016 |
| Первый результат всех категорий, p50 / p95, с | 4,953 / 15,000 | 4,016 / 20,016 |
| Основной LLM-этап с корректным результатом | 13/35 (37,14%) | 16/35 (45,71%) |
| Полностью завершённые LLM-стадии, включая объяснение | 2/35 (5,71%) | 6/35 (17,14%) |
| Полный ответ с учётом таймаутов, p50 / p95, с | 10,015 / 20,015 | 10,015 / 20,016 |
| Успешный полный LLM-ответ, p50 / p95, с | 4,078 / 8,328 | 4,047 / 9,421 |
| Корректность сценария, включая локальный fallback | 32/40 | 28/40 |
| Правильный инструмент в проверенных сценариях | 17/17 | 15/17 |
| Неподтверждённые факты, незапрошенные изменения, заказы | 0 | 0 |

Время первого результата включает локальные ответы: это метрика доступности результата пользователю, а не скорости самой модели. Основной LLM-этап означает корректное извлечение условий либо проверенное LLM-объяснение для запроса инструмента; необязательное объяснение после успешного извлечения может не успеть. Полный LLM-успех требует завершения всех нужных стадий. Ни один локальный fallback не засчитан как LLM-успех. Перцентили — nearest-rank; общий p95 включает допустимые 20-секундные альтернативы. Процентили только успешных вызовов приведены отдельно и не скрывают неудачи.

Метрика инструментов проверяет интеграцию: 14 сценариев объяснения/сравнения/деталей/альтернатив и 3 явные локальные операции. Выбор инструмента часто локален; модель выбирает проверенные основания. Это не 17 независимых успешных native tool calls модели. Нативные бизнес-вызовы по-прежнему не исполняются.

В проверке первоначального поиска исправлена ошибка оценщика: backend-поле `assumptions` описывает происхождение/defaults и не является незапрошенным изменением условий. Результат исправлен для обеих моделей без повторных облачных запросов.

Парный прогон выполнен после введения общего бюджета и отдельного объяснения. Последующие исправления отмены, timeout-fallback и HTTP/базы проверены регрессионными тестами. Поэтому эти числа не являются SLA финального HTTP-сервера. В исходном прогоне один ответ Haiku вышел за номинальный лимит на 0,297 с при закрытии соединения; именно этот класс задержки устранён тестом медленной отмены.

## Финальная проверка и выбор

`artifacts/latency-final-smoke.json`: пять реальных запросов на финальной логике — опечатка бюджета, пересборка, первый поиск, сравнение, альтернативы. Все пять прошли доменные проверки, без незапрошенных изменений и заказов. Только сравнение завершилось полным LLM-ответом (6,500 с); остальные получили доступные проверенные результаты при таймауте. Это отдельный smoke-тест логики, без HTTP/базы, не новый большой сравнительный набор.

Haiku не показала устойчивого превосходства по времени и надёжности: основной остаётся Luna. Условие переключения — повторяемое преимущество по p50/p95, не менее 95% корректных основных LLM-этапов, качество не ниже текущей модели, ноль неподтверждённых действий. Текущий прогон это условие не выполняет. Надёжные облачные 3–5 с пока не подтверждены.

Проверки интерфейса: 1440/768/390/320, реальные локальные поиск, сравнение и сортировка; отдельный контролируемый ответ провайдера проверяет независимое обновление панели, неудачную правку, сохранение текста, фокуса и карточек. Скриншоты: `artifacts/latency-ui/`. Контролируемая UI-проверка не засчитывается как реальный LLM-вызов.

Задачи объяснений хранятся в процессе. Штатный запуск — один worker; для нескольких нужны общая очередь/хранилище или закрепление маршрута за процессом. Потеря задачи при рестарте даёт локальные факты, а не новый платный запрос. Docker/PostgreSQL исполнением не проверены. Ключи, сырые ответы и заголовки в артефакты не записываются.

Воспроизведение: `python scripts/benchmark_latency.py` (платные запросы); `python -m pytest -q`; `python -m ruff check app scripts tests`; `node --test tests/*.test.mjs`; `python tests/latency_ui_verify.py` и `python tests/agent_ui_verify.py` против локального сервера.

Финальные проверки: 454 Python-теста passed, 22 JavaScript-теста passed, Ruff passed, проверка пробелов diff passed. Осталось прежнее предупреждение Starlette/httpx о совместимости TestClient. Текущий ключ не найден в проверенных файлах задачи и отчётах; `.env` исключён из Git. История Git в рамках этой задачи повторно не сканировалась.

## Уточнение источника задержек: сетевой путь и reasoning

Последующее расследование локализовало два фактора. Предыдущие проценты характеризуют связку приложения, настроек модели и сетевого маршрута, а не изолированную надёжность MultiAI или моделей.

**1. Неявное рассуждение средней глубины.** Авторизованный `/v1/models` сообщает для Luna и Haiku `reasoning.default=medium`, `allow_disable=true`. Приложение не передаёт `reasoning_effort`, поэтому наследует этот режим. Метаданные сохранены в `artifacts/provider-reasoning-catalog.json`.

Для одного и того же настоящего запроса объяснения, напрямую к прежнему MultiAI, с прежним ключом и Luna:

- Три повтора в каждой из двух сетевых конфигураций не завершили объяснение за 10 с. Разбор условий прошёл 3/3 в каждой конфигурации: напрямую 4,547–5,438 с, через прокси 5,250–6,782 с.
- Два отдельных контроля с обычным `max_tokens=1500` и reasoning по умолчанию не завершились даже за диагностические 25 с. Лимиты производственного приложения не увеличивались.
- С `max_tokens=256` пришёл корректный ответ за 15,516 с, содержавший отдельное поле рассуждений. Полезный JSON — 159 символов, completion usage — 307 токенов. Этот ответ также показывает, что нельзя считать заявленный max_tokens точным потолком всех токенов данного маршрута.
- Потоковая версия получила заголовки за 0,796 с, первый полезный текст — за 11,593 с, завершилась за 12,562 с. Ранние заголовки сами по себе не устраняют ожидание полезного ответа.
- Изменение только `reasoning_effort` на `none`, с исходным `max_tokens=1500`, дало четыре ответа Luna за 8,484 / 4,594 / 4,812 / 4,609 с. Рассуждений в трёх ответах с измеренной метаданной не было. Но только один ответ прошёл всю доменную валидацию; два последних нарушили ограничение длины `fact_ids`, первый также не прошёл схему. Эти ответы не засчитаны как успешные LLM-результаты.
- `low` дал корректный ответ за 14,906 с. Одна проба Haiku с `none` была корректна, но заняла 16,078 с. Отключение reasoning не гарантирует целевое время любой модели и требует проверки качества.

Это подтверждает существенное влияние лишнего reasoning на задержку воспроизводимого объяснения Luna. Простой переход на `none` без усиления формата ответа не является готовым исправлением надёжности. Отдельно остаются внутренние задержки маршрута, которые нельзя разделить на очередь MultiAI и вычисления его upstream без серверной телеметрии.

**2. Скрыто унаследованный системный прокси Windows.** Переменные окружения прокси пусты, но `urllib.request.getproxies()` и HTTPX обнаруживают прокси `127.0.0.1:10809`; процесс порта — Xray. `httpx.AsyncClient` по умолчанию использует `trust_env=True`. В одной минимальной пробе соединение через Xray остановилось на `proxy.start_tls` и закончилось ConnectTimeout за 14,422 с: запрос генерации ещё не был отправлен. Такой сбой не объясняется работой модели. Два прямых минимальных JSON-запроса прошли за 2,891 и 3,516 с. Другой запрос через Xray также успешно прошёл за 2,969 с, поэтому прокси нестабилен, а не постоянно недоступен.

Прокси не объясняет всю проблему: настоящее объяснение не укладывалось в 10 с и напрямую. Необходимы отдельно управляемый маршрут AI-клиента и проверенный режим reasoning/формат для технических стадий. Глобальные настройки Xray, `.env`, ключ, провайдер и производственный код в этом расследовании не изменялись.

Сетевые границы измерены [trace-расширением HTTPX](https://www.python-httpx.org/advanced/extensions/), без сохранения заголовков, ответов, текста рассуждений или ключей. Артефакты: `network-route-diagnosis.json`, `provider-path-probe.json`, `narration-bottleneck-probe.json`, `reasoning-causality-probe.json`, `reasoning-none-confirmation.json` в `artifacts/`. Пары production payload идентичны по SHA-256; менялся только путь соединения. Пробы reasoning отдельно фиксируют изменённый параметр.

### Повторная проверка с сохранённым VPN

Выполнено ещё 16 последовательных сетевых вызовов Luna: 12 с исходным reasoning по умолчанию и 4 с `reasoning_effort=none`. Провайдер, ключ и рабочая конфигурация не менялись. Повторяемая команда: `python scripts/retest_provider_path.py`; отдельная проверка режима: `python scripts/retest_provider_path.py --rounds 1 --effort none --output artifacts/provider-path-retest-none.json`.

В исходном режиме разбор условий прошёл 6/6: через системный прокси 5,000–5,984 с, в обход HTTP-прокси 4,312–4,657 с. Объяснение не завершилось за 10 с во всех 6 вызовах. Два из трёх объяснений в обход прокси остановились на TLS, остальные четыре вызова объяснения — после отправки запроса, в ожидании ответа.

С reasoning `none` разбор прошёл через прокси за 3,687 с; другой вызов разбора не успел, потратив 7,610 с на соединение до отправки запроса. Оба объяснения пришли за 5,594 / 4,922 с, но нарушили ограничение длины `fact_ids` и не засчитаны успешными.

**Важное уточнение маршрута:** `Find-NetRoute` к разрешённому адресу MultiAI выбрал `happ-xray` (Happ Tunnel), interface 54. Следовательно, `trust_env=False` отключает использование HTTP-прокси клиентом, но не отключает системный TUN. Обозначение `direct` в предыдущих артефактах также означает только обход HTTP-прокси; полноценного сравнения VPN-on/VPN-off оно не доказывает. Влияние VPN целиком пока не изолировано. Пользователь явно выбрал оставить VPN включённым; глобальные настройки не менялись. Называть VPN основной причиной на основании этих данных нельзя.

Артефакты: `artifacts/provider-path-retest.json`, `artifacts/provider-path-retest-none.json`. Регрессионные проверки после повтора: 27 Python-тестов (deadline, блокировки базы, объяснения, транспорт) и 4 JavaScript-теста прошли; сохранилось прежнее предупреждение Starlette/httpx. Производственный код в этой повторной диагностике не изменён.
