# Сравнение моделей MultiAI

Этот отчёт описывает первоначальные сравнения. Последующая переработка backend и окончательные результаты приведены в [отчёте об исправлении намерений](backend-intent-fix.md).

Провайдер проверен по реальному `/v1/models`, затем выполнены запросы Chat Completions с ключом из локального `.env`. Ключ не включён в отчёты. Исходные результаты Polza сохранены.

## Выбор для приложения

В `.env`, `.env.example` и Docker Compose выбран `deepseek-v4.1-flash`, адрес `https://multiai.store/v1`. Backend перезапущен с новым окружением. Проверка через настоящий HTTP-интерфейс приложения вернула режим `llm`, три предложения и запрошенные бюджет 300 000 рублей и завтрак. Демонстрационный заказ этим тестом не создавался.

| Модель | Понимание намерений отдельно | Основные сценарии приложения | Неформальные запросы приложения |
|---|---:|---:|---:|
| gpt-6.1-terra | 8/8 | 22/24 | 5/10 |
| gemini-3.8-flash | 8/8 после обработки JSON-оболочки | 22/24 | 5/10 |
| deepseek-v4.1-flash | 8/8 | 23/24 | 5/10 |

Основной и первый неформальный прогон выполнены **до исправления JSON-оболочки**. В основном наборе 12 из 24 шагов каждой модели выполнены локальными правилами без API: их успех не свидетельствует о качестве модели. В неформальном наборе такой шаг один из десяти. Итого результат приложения до исправления: GPT и Gemini 27/34, DeepSeek 28/34.

Медиана времени сетевого вызова в основных/неформальных сценариях: GPT 11,44/9,17 с, Gemini 14,43/5,40 с, DeepSeek 2,62/2,34 с. Часть прогонов пересекалась по времени; эти значения описывают наблюдение, а не изолированный нагрузочный тест или SLA. Число запросов без HTTP-ответа в пределах таймаута: GPT 2/21, Gemini 5/21, DeepSeek 1/21. Таймаут — 30 секунд; это не обязательно означает, что провайдер не обработал или не списал запрос.

DeepSeek выбран за лучшее сочетание результата и наблюдаемой задержки в этом малом наборе. Это не доказательство универсального превосходства. У разных моделей отличаются поля `usage`; стоимость в рублях не вычислялась из неизвестных биллинговых единиц.

## Исправленная совместимость Gemini

Gemini иногда отдаёт JSON внутри полного Markdown-блока, несмотря на `response_format=json_object`. Первый прямой прогон: 1/8; повтор без исправления: 0/8. Диагностика показала правильное содержимое в неверной оболочке. Добавлена функция, принимающая обычный объект JSON или один полный блок `json`. Текст вокруг блока, неполный блок, другой язык и значения, не являющиеся объектом, отклоняются. Проверки полей и ограничений приложения сохранены.

После исправления отдельный тест понимания Gemini: 8/8. Повтор неформальных сценариев приложения: 5/10; восемь из девяти сетевых запросов не вернули HTTP-ответ в пределах таймаута. Этот прогон пересекался с основным сравнением, поэтому по нему нельзя отделить влияние параллельных запросов от провайдера. После завершения всех сравнений одиночные последовательные проверки настоящего парсера успешны: Gemini — 16,418 с, DeepSeek — 3,257 с. Они сохранены в `artifacts/multiai-serial-probes.json`.

## Проверенные формулировки и оставшиеся проблемы

Проверялись формальные запросы, «бюджэт 140 тыщ», сумма словами, «пёс едет с нами», «мелкому 6 лет», желательные и обязательные завтраки, перенос даты, сохранение выбранного отеля, уточнение состава детей, неподдерживаемое направление, попытка изменить правила модели и вопрос «пока ничего не меняй».

Смена провайдера не исправляет старый механизм слияния результатов модели и правил:

- Модель может правильно распознать собаку, возраст или опечатку, но словарная проверка доказательства отвергает изменение.
- Локальный разбор упоминания Сочи перекрывает намерение «Сочи не хочу, давай в Прагу».
- «На пару дней попозже» иногда вызывает локальное уточнение до обращения к модели.
- Желательность завтрака в свободной формулировке может не примениться.

Полный контракт действий `change/hypothetical/clarify` проверялся только отдельным экспериментом. Он ещё не заменяет продукционный парсер. Результат 8/8 нельзя выдавать за готовность произвольного диалога в приложении. Для существенного улучшения нужен отдельный пересмотр извлечения и применения намерений, с защитой гипотетических вопросов от изменения поездки.

## Проверка кода и воспроизведение

### Дополнительная диагностика: Qwen и Claude

Повторено 8 прямых проверок для `qwen3.8-flash` и `claude-haiku-5-5`, затем 5 выбранных сложных запросов через приложение: собака, возраст ребёнка, бюджет, желательный завтрак и смена направления.

- Qwen: прямое понимание 8/8, все ответы HTTP 200, медиана 3,243 с; приложение 1/5 при пяти HTTP 200. Это выбранные проблемные случаи, а не новый полный набор из 34 шагов.
- Claude: только один из восьми прямых запросов получил HTTP 200 и прошёл проверку; остальные завершились ReadError/ConnectError/ConnectTimeout. Это не доказательство плохого понимания модели и не позволяет приписать сбой именно MultiAI. В приложении 1/5, HTTP 200 получен на четырёх из пяти вызовов.

Записанные ответы DeepSeek и Qwen показывают правильные предложения `pets=true`, `children_ages=[6]`, `breakfast=true` с приоритетом `preferred`, которые продукционный обработчик не применяет. Причины локализованы в `app/parser.py`: словарный FIELD_EVIDENCE, запрет изменения силы предпочтения без совпадения с локальным разбором и безусловный приоритет `patch | rules.patch`. Ранний выход при `rules.questions` также не даёт модели обработать часть относительных дат. Удалять проверки целиком нельзя: они защищают от неподтверждённых изменений. Следующий этап — структурированное намерение с независимым различением изменения, сравнения и уточнения, проверкой значений и сохранением контекста.

Основная модель в `.env` оставлена DeepSeek. Дополнительные артефакты: `artifacts/multiai-extra-direct.json`, `artifacts/multiai-extra-app.json`. Продукционное поведение в рамках этой дополнительной диагностики не изменялось.

284 автоматических теста прошли; Ruff прошёл. Есть прежнее предупреждение о совместимости Starlette TestClient/httpx. Docker в этой среде не запускался.
